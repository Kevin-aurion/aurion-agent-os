# L7 L7 模型網關層（LiteLLM 類開源、路由、四維帳本、快取）

**策略**：🟩借用起步＋自研帳本（🧠借用5／💰採購0／📚文獻43／⚠️缺口11）。定案 LiteLLM（MIT 核心）為 control-plane 起點——Provider Adapter、virtual key、路由生態最完整；但兩來源共同診斷其 spend/budget 用 Float 且有 check-then-write race——帳本自建：原子 reservation（預扣→執行→結算）、tenant/project/agent/tool 四維計量、預算硬上限 fail-closed。高效能候選 Bifrost／Envoy AI Gateway（Apache-2.0）保持介面可抽換。快取分 exact（直接上）與 semantic（GPTCache 模式，先 shadow 驗證誤中率才啟用）。new-api 因 AGPL 淘汰。

## 🏗️ 自研開發 Spec

自研核心為四維帳本與路由引擎：API Protocol Adapter（正規化OpenAI/Anthropic多協議）、Identity Resolver（僅信任virtual key/JWT claim）、Policy/Capability Filter（三類硬性pass/fail篩選）、Cost Quoter（pre-flight quote_id）、Budget Reservation Engine（PostgreSQL SELECT FOR UPDATE原子reservation，staged reservation，HELD→CAPTURED/RELEASED/EXPIRED狀態機）、Candidate Registry、Health Monitor/Circuit Breaker（UNKNOWN→HEALTHY→DEGRADED→OPEN↔HALF_OPEN）、Route Scorer（multi-objective加權+top-K抽樣）、Retry & Fallback Executor（三層chain）、Provider Adapter、Cache Layer（L1 exact hash+L2 semantic embedding/ANN，shadow mode）、Usage/Trace/Ledger Emitter（OTel GenAI semantic convention）。核心資料模型：dim_tenant/dim_project/dim_agent/dim_tool正交維度、pricing_catalog（NUMERIC(30,12)禁用Float）、budget_policy/budget_balance（BIGINT amount_nusd）、cost_quote、reservation（UNIQUE idempotency_key）、usage_event（append-only）、route_attempt（全候選稽核）、semantic cache namespace複合key。四維為正交約束非乘法計費，一次呼叫只debit一次錢包。

## ❌ 反模式（要避免）

- 把 LiteLLM 內建 spend/max_budget 當成零超支的財務帳本真相來源——欄位多為 Float、spend logging 為回應後非同步寫入，天生存在 check-then-write race，無法達成真正硬上限
- 直接把 LiteLLM 內建 semantic cache 或任何單一廠商語意快取原封不動上生產——codex 明確指出 LiteLLM 原生方案「僅適合 prototype」，量產前必須自建 policy layer 並先跑 shadow mode
- 一開始就把整條 fallback chain 的最壞情況成本全部預先凍結——應採 staged/incremental reservation，只在 fallback 真正被觸發時才追加訂位
- 把 capability/policy/financial/runtime/compatibility 等硬性條件併入加權分數，而非做 pass/fail 硬篩選——會讓不合格候選靠其他維度分數「翻盤」中選
- 信任 client 自填的 tenant/project/agent/tool 身分 header，而非一律從已驗證 virtual key/JWT claim 解析
- 多實例部署卻不共用 Redis——會導致各實例 rate limit/router 狀態不一致、budget 執行不同步
- 高流量下每請求同步寫 PostgreSQL 記錄 spend/usage——會造成 DB 熱點；即使改批次 flush + Redis transaction buffer，也不能取代原子 reservation 解決硬上限問題
- 更換/輪替 LiteLLM 的 `LITELLM_SALT_KEY`——會讓所有既存加密的 provider credentials 永久無法解密
- 生產環境用 SQLite 當 LiteLLM 後端資料庫——無法安全處理併發 budget 檢查的 race condition
- 用浮動 tag（而非釘選精確 image digest 並驗簽）部署所借用的 OSS gateway 元件——2026 年已有真實 PyPI 供應鏈 compromise 事件與多起 CVE
- 把 gateway 內建的 provider price map 當成對帳用的財務真相——應自建獨立版本化的 pricing_catalog 並對照 provider 實際帳單
- 採用 new-api 作為核心 Agent router/帳本——兩來源都認定其功能定位是 API 分發/充值/營運後台而非 Agent-level router；grok額外指出AGPL-3.0授權若嵌入閉源核心有法務風險
- 把任何單一廠商自我揭露的效能宣稱（如 Bifrost 「比 LiteLLM 快 54 倍」、Portkey 「<1ms latency」）當成可直接拿來做決策的數字——須自行 trace replay 驗證
- 對所有 agentic 請求無差別套用 semantic cache——含 tool side effect、即時資訊、PII、高 temperature、RAG 版本不穩定的請求都應該預設 bypass/no-store
- 依賴 LiteLLM 預設關閉的 background health check 做故障保護——當所有 deployment 都判定 unhealthy 時會「safety bypass」回傳全部 deployment，可能靜默把流量導到已掛掉的 endpoint
