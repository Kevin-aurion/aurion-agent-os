# L2 編排層（多 Agent 協作、結構化交接、HITL、耐久執行）

**策略**：混合：🟢借用雙引擎（LangGraph＋Temporal）為執行底座 ＋ 🔴自研（Handoff/Worker 協議層、HITL 審批服務、Contracts 契約庫、Effect Ledger）；🔵採購僅選配商用 LLM API（供 L2 驗收流水線的 Semantic Gate/LLM-as-judge 使用，非必要、非核心）

## 💰 需採購 / 外部授權

- 商用 LLM API（供選配的 Semantic Gate / LLM-as-judge 使用）：驗收流水線設計含 Schema validate→Policy checks→Semantic gate（可選 LLM-as-judge）→HITL；若採用 LLM-as-judge 需呼叫商用 LLM API，但這屬於 L1 模型層而非 L2 編排層本身的採購需求，L2 編排引擎本身完全可自架，此項僅為可選、非必要

## 🏗️ 自研開發 Spec

L2a Durable Runtime (Temporal) 負責 run identity、retries、timers、queues、crash recovery、長時間等待、saga、跨服務交易；L2b Agent Orchestration (LangGraph) 負責 reasoning graph、tool policy、HITL interrupt、memory、structured handoff、context 隔離，以「業務步驟=Activity、認知步驟=node」劃界整合。自建模組含 Runtime（Run 生命週期管理）、Graph（可直接採用 LangGraph 或實作 isomorphic 版本）、Handoff（Transfer 協議層，仿 OpenAI Agents SDK handoff()）、Worker（Delegate 協議層，仿 Claude subagent 強隔離語意）、HITL（Approval service+resume tokens+timeout 升級狀態機）、Durable（Temporal worker adapters）、Contracts（WorkOrder/WorkResult/HandoffEnvelope/ApprovalRequest 等 versioned schema 集中管理）、雙層 Memory（checkpoint thread-scoped + store cross-thread，與 Effect Ledger 分離存放）、Effect Ledger & Compensation Registry（append-only 已提交外部副作用紀錄+逆向補償 handler 目錄）、Large Payload Bridge（因 Temporal 2MB payload 限制外接物件存儲）。核心資料模型：WorkOrder/WorkResult（委派契約，含 idempotency_key/budget）、HandoffEnvelope（轉移契約，destination-specific schema 驗證）、ApprovalRequest/ApprovalDecision（HITL）、Thread/Checkpoint/Store 三層概念、Effect Ledger entry 與 Compensation registry entry（saga 補償）。

## ❌ 反模式（要避免）

- 不可用 bare try/except 包住 LangGraph interrupt（會靠特殊 exception 冒泡，破壞控制流）
- 不可在 node 內條件式跳過或重排 interrupt（resume 依 index 配對，順序改變會配對錯誤）
- 不可用 while True 迴圈搭配多個 interrupt 做重複驗證（會指數重放；應改用 conditional edge 重進 node）
- interrupt 前的 side effect 未做冪等處理（node 會從頭重跑，重跑會重複執行副作用）
- 把靜態 breakpoint (interrupt_before/interrupt_after) 當作生產 HITL 機制使用（官方僅建議用於 debug）
- 把完整 LLM transcript 直接塞進 Temporal workflow payload（會撞 2MB 限制，應改用物件存儲+參照 ID）
- 把整個 agent graph 塞進單一 Temporal Activity（喪失細粒度 replay 能力）
- 把每個 tool call 都包成獨立 Temporal Activity（過度細粒度，overhead 過重）
- 只用 CrewAI/AG2 的對話式協作機制當 production 狀態機核心（缺嚴格 checkpoint/HITL 工程保證）
- 只靠 LangGraph checkpointer 當作跨服務交易與長時間審批的唯一底座（interrupt 預設無限等待，無 durable timer/timeout 升級機制）
- 把 Delegate（call，不轉移控制權）與 Transfer（handoff，轉移控制權）兩種語意混用同一套命名或介面
- 假設補償等同「重跑一次反向 LLM 呼叫」——LLM 步驟本質不可逆且昂貴，補償應設計為業務狀態層級回滾
- Temporal signal timeout 分支誤以「signal 是否存在」判斷而非以 await 回傳值為準（晚到 signal 仍可能進 history，造成競態 bug）
- 未經法務審查就將 Claude Agent SDK 核心 runtime 直接嵌入生產系統（其 Commercial ToS 限制未評估）
- 引用 CrewAI「token overhead ~18%」「60% Fortune 500 採用」等未經官方稽核的廠商/第三方宣稱數字作為工程決策依據
- 把 LangGraph Cloud「數百 MB payload」等行銷敘述當作可承諾的 SLA/自架系統設計基準
- 選用 Inngest 時忽略其 server 端 SSPL/DOSP 授權與「純開源自架」原則的摩擦，未經法務確認就直接採用

## ⚠️ 查證缺口（誠實標注）

- codex 背景調查任務確認未完整跑完：實地核對 scratchpad 後確認整合文本未寫出，其獨有結論應視為未完成佐證的線索
- Temporal「50MB event history/50000 events」數字：codex log 確認曾搜尋但未留下確認結果，grok 完整報告通篇未提及此數字，只確認 2MB payload/4MB gRPC message 有官方佐證
- 【明確標注的矛盾點】Microsoft AutoGen 現況判定：codex 認為 AutoGen (Core) 是更底層通用協定基礎設施，未提及 maintenance mode；grok 引用第三方部落格佐證已進入 maintenance mode，需人工至官方 repo 查看最新 README/commit 公告確認
- Temporal 官方 LangGraph 整合模組 temporalio/contrib/langgraph 與 OpenAI Agents SDK 整合模組：僅 codex 提及但未留下 fetch 結果內容，grok 完全未提及，需實際開啟路徑確認模組是否存在
- Claude Agent SDK 文件網域不一致：codex 與 grok 引用兩個不同網域，需人工實際開啟確認何者為當前權威文件站
- CrewAI「token overhead ~18%」「60% Fortune 500 採用」數字：grok 原始報告已明確自我標註為第三方宣稱，不可採信為工程依據
- LangGraph checkpoint 每秒吞吐量、Temporal history 在特定硬體下的效能基準：兩來源均明確表示未查到可信公開數字，若為容量規劃關鍵輸入需自建 benchmark
- Temporal「signal 或 timeout」競態條件處理細節僅見於個人部落格引用，並非 Temporal 官方文件直接佐證，正式採用前建議二次確認
- Inngest 的 SSPL/DOSP 授權條款是否實質限制自架/內部商用場景未經法務確認，兩來源只點出授權類型與定性判斷
- Claude Agent SDK 的 Commercial ToS 具體條款內容（哪些使用情境會觸發限制）兩來源都只提及需法務評估，未展開條款細節
- 兩來源都沒有討論多租戶 (multi-tenant) Agentic OS 下多個 Temporal namespace/cluster 或多個 LangGraph deployment 如何對應隔離，此為皆未觸及的空白
