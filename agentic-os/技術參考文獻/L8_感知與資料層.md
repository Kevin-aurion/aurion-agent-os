## 🏗️ 自研開發 Spec

自研核心為 Ingestion Pipeline：Ingest API/Webhook、Job Queue（Redis Streams/NATS/RabbitMQ/Kafka，at-least-once+冪等消費）、Classifier（文字覆蓋率門檻判斷掃描件）、Parser Router（Light/Heavy/WebFetch三路由，confidence過低自動升級）、Light Extract Path（原生文字PDF直抽）、Heavy OCR/VLM Path（獨立GPU佇列）、Web Fetch/Search/Browser Plane、Canonical IR Store（版本化，保留bbox/page/階層/provenance）、Chunker（結構優先於token長度）、Embed Workers、Vector+BM25+Metadata混合檢索DB、DLQ（死信佇列觸發自動升級或人工介入）。核心資料模型：Canonical IR/ParsedDocument（pages/blocks/bbox/relations）、Chunk（含prev/next鄰居鏈、quality信心分數）、Content-addressed快取Key（cache_key→chunk_key→embed_key逐層雜湊）、s3佈局content-addressed、表格以parent+child chunks表示、跨頁關係用continued_from連結而非硬拼接。Parser Backend介面須可插拔，Parse/Chunk/Embed三層解耦各自版本化。

## ❌ 反模式（要避免）

- 把 Markdown 當作 canonical/唯一儲存格式——它是 lossy 中間格式，會丟失 bbox 座標、表格結構與 provenance 資訊，Docling 官方明確反對此作法
- 把 GPL-3.0 授權的專案（如 Marker）鏈入閉源核心系統，有授權感染（copyleft）風險，且其 Model 授權（修改版 OpenRAIL-M）對商用另有限制
- 略過版本化快取設計，導致只是調整 chunk 參數或更換 embedding 模型時，被迫重跑整個昂貴的 VLM parse 流程
- 所有文件不分青紅皂白都跑 Heavy VLM 解析（即使是原生可抽取文字的 PDF），造成 GPU 資源浪費——應先分流 Light path
- 將 DOCX/PPTX/XLSX 等原生格式文件先轉檔成 PDF 再解析，而非使用原生格式的 parser，會損失結構資訊
- 將輕量（light）與重量（heavy VLM）解析任務放進同一個佇列，導致簡單 PDF 被大型 VLM 任務阻塞，拖慢整體吞吐
- 把 vendor 自我宣稱的 benchmark 數字（例如 PaddleOCR-VL-1.6 聲稱的 96.3%）當作官方 leaderboard 已驗證的數字直接寫入 spec 或對外文件
- 把跨版本（如 OmniDocBench v1.5 vs v1.6）的分數直接並列比較當作同一把尺——評測方法論與資料集已變動，橫比會導致誤判
- 未經法務審視就直接將 AGPL-3.0 專案（SearXNG、Firecrawl）的自架部署方式視為『絕對安全、無需揭露原始碼』

## ⚠️ 查證缺口（誠實標注）

- 【最關鍵】本次並非真正的雙軌獨立調查：標記為「claude-fallback」的來源自述因codex調查逾時未完成，改為重新標記自「grok」來源的調查結果，兩份輸入實質同源，不構成獨立交叉驗證，建議日後另外補一次真正獨立的調查

- PaddleOCR-VL-1.6 宣稱 >96.3% 為 vendor 自報（2026-05/06文案），官方 v1.6_full 主表當時僅列1.5版=94.93，1.6版是否已納入官方leaderboard重跑結果待核實
- MinerU 的新 license（自訂、Apache-based+附加條款）具體條款全文，兩來源都僅有文字描述、未附直接連結核實，正式開工前必須直接查閱其 LICENSE 檔案
- SearXNG、Firecrawl 的 AGPL-3.0 copyleft 義務邊界，兩來源都只提醒「需法務審視」，沒有給出確定法律結論
- Playwright 等反偵測手法對 Cloudflare 等主流防護的實際成功率，兩來源皆指出「無穩定公開 benchmark」，此為已知能力缺口
- 各 repo 的 star 數（如 MinerU、PaddleOCR 等）僅為調查當下的約略快照且會持續變動，不應以星數作為主要決策依據
- olmOCR 宣稱的「<$200/百萬頁」成本數字來源為官方 README/blog 自報，兩來源均未提供第三方或獨立驗證來源
- 兩來源皆以 OmniDocBench v1.6_full 作為主要比較基準，v1.5 與 v1.6 版本間分數不可直接橫向比較，若手上有v1.5時期舊資料需注意版本錯配風險
