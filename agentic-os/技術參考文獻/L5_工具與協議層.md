# L5 L5 工具與協議層（MCP 深入、MCP Gateway、A2A、工具權限）

**策略**：🟪混合（🧠借用7／💰採購1／📚文獻57／⚠️缺口12）。定案：MCP 只定義 mechanism 不含 policy——治理靠自建 Gateway 層。Docker MCP Gateway（MIT，開發環境沙盒化跑 MCP server）＋ IBM ContextForge（Apache-2.0，組織級 control plane：virtual server 組合、token scoping、審計）互補。工具權限核心模式：query／sandbox／prod 三分權 connector（學 Airwallex）＋風險分級（唯讀→低危→高危需 HITL）＋JIT 短效憑證。A2A 只用於跨組織 opaque 邊界，內部子 agent 走編排層結構化交接即可，不要為用而用。🧠補查更新：ContextForge GA矛盾裁決——已正式GA（v1.0.0，2026-05-01；最新v1.0.5，2026-07-07，含A2A Compatibility），codex正確、grok查到的是舊RC資訊；定案不變，且其A2A相容性正好覆蓋L0 registry部分需求。

## 💰 需採購 / 外部授權

- 企業 OIDC/OAuth 2.1 Identity Provider（既有企業SSO／Entra ID／Okta／Auth0 等）：兩來源描述MCP OAuth流程時都以「已存在外部Authorization Server」為前提，codex並指出Microsoft MCP Gateway走Entra整合路線；若組織尚無IdP，短期內以採購/沿用既有企業SSO代替自架評估是務實選擇，長期是否能自架仍待技術驗證，此為推論非兩來源明確建議

## 🏗️ 自研開發 Spec

自研核心為 Gateway 各模組：Protocol/Transport Adapter（stdio與Streamable HTTP可替換介面）、Session/Lifecycle Manager（initialize協商、Origin驗證、127.0.0.1綁定）、Virtual Server/Catalog Aggregator（`{serverSlug}.{toolName}`統一命名）、Identity Provider Adapter（OAuth 2.1/RFC9728/RFC8414/DCR）、Policy Engine(PDP/PEP，建議OPA/Rego或Cedar，list與call雙重檢查防TOCTOU)、Credential Broker（JIT短效憑證、CredentialRef不落地明文、禁token passthrough）、Sandboxed Runtime Manager（容器隔離、read-only rootfs、default-deny egress）、Audit & Observability(OTel，含argumentDigest不存明文)、Registry/Admission Controller（Internal Curated Registry含digest+SBOM+risk分級）、Output Guard/DLP、A2A Adapter（僅跨組織邊界啟用）。核心資料模型：ServerRegistration/ToolPolicyMetadata(riskTier分級三來源不一致需定案)/PolicyBinding(OPA/Cedar承載)/InvocationAudit(僅存digest)/ApprovalRequest(canonical preview、單次使用)/AgentCard與Task(A2A狀態機)。介面設計採12步驟(codex)或精簡版(grok)Gateway Request Pipeline，401/403協議層拒絕與`isError=true`業務失敗分離。

## ❌ 反模式（要避免）

- 把mcp-proxy這類純transport轉接工具當成完整企業級Gateway使用——缺registry、identity、PDP、per-tool authorization、token broker、sandbox、audit，兩者不能互相替代
- 可從web端觸發、且能任意spawn stdio command的proxy設計——可能把單純XSS升級成host RCE（MCP官方安全文件明確警告）
- 只靠MCP自帶ToolAnnotations（readOnlyHint/destructiveHint等）做正式安全授權依據或當ACL使用——這些只是server自報的hint非強制安全邊界，正式授權須靠Gateway自有risk metadata+OAuth scope+PDP policy+runtime sandbox
- 把A2A當成「進階版的MCP tool call」濫用在確定性查詢/單次動作場景——穩定JSON Schema、一次請求完成的場景應該用MCP Tool，A2A僅適用需維護跨輪狀態、opaque internal state的remote agent邊界
- 從Official/public MCP Registry直接auto-run第三方server，未經internal curated registry過濾（digest pinning、SBOM、risk分級）
- 用單一connector帶environment參數（如`env=prod`/`env=sandbox`）切換讀寫範圍，而非用三個物理獨立security principal分權——model可能僅改一個參數就把sandbox呼叫升級成production呼叫
- Token passthrough給downstream API（MCP規格明文禁止）；或把精細授權判斷責任錯誤下放給只拿到粗粒度token的下游MCP server自己做，而非由Gateway集中做ToolPolicy
- Query-only/唯讀場景的agent仍採「先list出全部工具、執行時才deny高風險工具」——應在capability/list階段就依權限過濾掉高風險工具，降低prompt injection攻擊面
- 把授權失敗（401/403協議層拒絕）與工具業務執行失敗（`isError=true`）混為一談處理，剝奪model自我修正業務錯誤的機會
- 把「150+ supporting organizations」「三大雲平台整合」等生態層級宣稱直接等同於「production deployment數量」或「產業已普及」的證據
- 引用vendor自報效能數字（如agentgateway的300×/35×宣稱來自Solo.io產品頁、ContextForge的RPS數字來自官方文件）時不標注來源，或拿不同專案的自報數字互相比較當作公平benchmark
- 同時全量部署兩套治理平面（如同時上ContextForge又上agentgateway做policy決策）造成policy分裂、責任歸屬不清

## ⚠️ 查證缺口（誠實標注）

- ⚠️矛盾（IBM ContextForge成熟度）：codex查到「v1.0.5(2026-07-07)已發布、v1.0.0已GA」；grok查到的版本標籤是「v1.0.0-RC」（尚未GA）。兩者對同一專案release狀態描述直接衝突（此矛盾已於後續補查裁決為已GA，見strategy）
- ⚠️矛盾（Risk Tier分級顆粒度）：codex用三級(READ/LOW_WRITE/HIGH_RISK)，grok用四級(R0/R1/R2/R3)，精神一致但顆粒度與命名不同，需architect定案採用哪套或如何合併
- MCP版本基準的實務語氣落差：codex主張以2025-11-25為production基準；grok稱2025-06-18為「常見protocolVersion」，2025-11-25僅是「現行latest schema」，建議實作時做protocolVersion向下相容協商而非寫死單一版本
- Gateway專案覆蓋不交叉：ToolHive、Microsoft MCP Gateway僅codex查到；agentgateway、MCP Gateway & Registry(agentic-community)僅grok查到；只有Docker MCP Gateway/ContextForge/mcp-proxy被兩者共同驗證，agentgateway效能宣稱需人工二次查證
- 效能數字全屬vendor自報：ContextForge的RPS數字、agentgateway宣稱、Docker Catalog的200+ tools等，皆無跨專案第三方公平benchmark，不可作為選型量化依據
- Official MCP Registry的GA狀態：兩來源一致確認截至查核日(2026-07-20)尚未GA(API v0.1 freeze/preview)，此狀態會隨時間變動需持續追蹤
- A2A實際production規模不明：兩來源都只查到生態級宣稱，缺乏具體production throughput、任務成功率或台灣企業實際案例數字
- 自架IdP(Keycloak/Ory/Zitadel等)可行性未評估：兩來源都沒有評估自架IdP是否能滿足MCP 2025-11-25新增的incremental scope、Client ID Metadata Document等機制
- Credential Broker/Secret Manager具體自架選型未涵蓋：除ContextForge內建的token scoping外，兩來源都沒有評估獨立自架secret manager(如HashiCorp Vault OSS版、Infisical)與Gateway的整合模式
- K8s環境下ToolHive vs ContextForge vs Microsoft MCP Gateway缺乏實測比較，屬待補查的實作驗證工作
- stdio transport需要使用者級身份區分時的替代方案未查明：兩來源一致認為stdio不適用OAuth，但都沒有說明使用者級身份/授權區分的替代做法
- 部分社群方案未列入正式建議：grok調查中提及MCPJungle等社群方案，因未能取得可核對的stars/repo資訊而未列入正式建議清單
