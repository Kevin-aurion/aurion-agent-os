# L9 L9 交付與商模層（多租戶、用量計費、私有化交付）

**策略**：🟨混合（🧠借用10／💰採購1／📚文獻30／⚠️缺口9）。計費雙引擎：OpenMeter（Apache-2.0，用量事件聚合）＋ Lago（訂閱/發票最完整，AGPL 需法務評估）。多租戶走 Pool→Bridge→Silo 漸進隔離：預設 shared schema＋RLS，大客戶升級獨立 schema/DB，isolation_mode 設計成可遷移。Feature flag 經 OpenFeature（CNCF）抽象呼叫、provider 可替換。私有化交付：Helm＋OCI registry＋license 在線心跳＋離線簽章雙模。RaaS 按結果計價的關鍵：Outcome Judge 獨立於執行 agent（防球員兼裁判），驗收 state machine＋Pilot 達標才開 billing——搭配崗位級 KPI（首輪通過率/人工介入率/每成果成本）。

## 💰 需採購 / 外部授權

- Replicated：商業私有化交付平台，提供air-gap Helm打包+license綁定的完整企業級交付體驗。兩來源均查無完全開源且對等的端到端私有化交付平台，僅在團隊資源有限、需快速達到企業級交付體驗時才建議採購評估；預設仍應以Helm+OCI registry+Keygen或自研license機制自行拼裝。Metronome同樣是商業SaaS但兩來源均明確不推薦（已被Stripe收購、不符自架原則），故不列入buy

## 🏗️ 自研開發 Spec

自研核心含 Metering Service（對接OpenMeter）、Billing & Catalog Service（對接Lago）、Entitlements Service、Tenancy Control Plane（Tenant/TenantResource/Membership/Quota四張表，isolation_mode可漸進調整）、Feature Flag Gateway（OpenFeature包裝底層provider）、Outcome Judge（獨立於執行agent的結果判定模組，禁止執行者自行回報結果觸發計費）、License & Delivery Service（online心跳+offline JWS簽章+device activation+grace period）、Sync Gateway（盒子↔雲，僅grok提出的待驗證提案）、SLA/Acceptance Engine（state machine追蹤task生命週期，計算並凍結驗收指標）。核心資料模型：Tenant(isolation_mode: pool|schema|silo)、TenantResource、Membership、Quota、UsageEvent(CloudEvents信封)、BillableEvent(借鏡Lago，transaction_id去重)、OutcomeEvent(RaaS核心，須由獨立Outcome Judge寫入，含acceptance_window_hours 24-72h)、Entitlement、LicenseFile(ed25519簽章JWT/JWS)、AcceptanceMetric(participation/resolution/first_pass/human_intervention/escalation/revocation rate、cost_per_resolution)。三層定價模式：Platform/seat固定費+Usage用量費+Outcome結果費，escalation不計outcome fee。

## ❌ 反模式（要避免）

- 不可用執行agent自己回報的結果直接觸發outcome billing——必須有獨立Outcome Judge模組寫入，否則等同球員兼裁判，是RaaS計費最大的誠信風險
- 不可跨廠商直接比較resolution rate等指標——Intercom Fin與Sierra的「resolution」定義方法論不透明且不一致，合約中須自行鎖定己方定義
- 不可把OpenMeter/Lago等專案官方宣稱的效能數字當作已驗證的benchmark直接寫入SLA承諾——皆為廠商自述或第三方轉述，須自行實測後才能對外承諾
- 不可硬編碼單一tenant isolation模式——應在資料模型保留isolation_mode欄位支援pool/schema/silo漸進遷移
- 不可在盒子→雲的usage/billing同步中傳輸原始客戶資料——僅能上傳聚合後的metering數據，避免違反私有化部署客戶對資料不落地/不出境的承諾
- 不可選用AGPL-3.0等copyleft授權專案，卻未經法務評估就直接整合進閉源商業產品——Lago、Flexprice、以及grok指稱的Unleash皆屬此類
- 不可把Keygen這類Fair Source License(FCL)專案當作標準OSI開源專案處理——FCL帶有時間限制的商業條款，不能與Apache/MIT/BSD混為一談
- 不可未定義「resolved/outcome」就貿然上線outcome billing——須先經Pilot驗證期凍結定義、設門檻、連續達標後才開放
- 不可把Metronome當成可自架選項研究或依賴——它已是Stripe旗下純SaaS商業產品，不符合團隊自架原則，僅能作架構參考

## ⚠️ 查證缺口（誠實標注）

- 【矛盾】Unleash授權：claude-fallback稱Apache License 2.0；grok稱AGPL-3.0，兩來源直接衝突，需人工查證官方GitHub repo的LICENSE檔案，此問題不解決不可定案
- 【矛盾/數字落差】Lago事件擷取效能：claude-fallback稱第三方文章引用約15,000 events/秒；grok稱Postgres路徑約10,000events/秒、遷移ClickHouse後約1,000,000events/秒，需直接查閱官方文件與ClickHouse blog原文核實並自行負載測試
- 「盒子＋雲」混合同步架構是否有可借鑑的既有標準：claude-fallback明確表示查無公開開源參考架構或標準協議，grok提供的具體設計未附既有業界標準來源連結，應視為待驗證自研提案
- RaaS（按結果計費）事件schema是否有官方標準：兩來源都確認查無官方/標準化的outcome-based事件schema規格，需團隊自行定案並在OpenMeter/Lago之上客製化實作
- License驗證機制缺乏成熟開源函式庫：兩來源都未找到「傳統OSI開源、生產成熟、可直接自架」的完整替代方案，是否採用Keygen或走自研路線需法務與工程共同定案
- 「數位員工」崗位級SLA/驗收指標缺乏公開產業標準：兩來源一致確認查無ISO等級或業界聯盟發布的通用框架，需團隊自行定義並在合約中明確鎖定
- Feature flag、多租戶的官方API/資料模型細節：claude-fallback指出搜尋結果未提供可直接引用的官方文件連結，需直接查閱各專案官方docs取得可開工等級的規格細節
- 產業用量/成效數字的原始出處未逐一查核：claude-fallback引用unthread.io數字與grok引用Intercom Fin/Sierra數字，均為第三方部落格或廠商自述，兩組數字彼此也沒有交叉驗證
- 部分項目授權/成熟度細節僅單一來源提及，未經交叉驗證：OpenMeter明確授權、GrowthBook、OpenFeature、Keygen、Replicated等僅grok提及；vmware-labs/distribution-tooling-for-helm僅claude-fallback提及，定案前建議至少各自快速核實一次官方repo
