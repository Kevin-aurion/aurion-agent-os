## 1. MemOS（MemTensor）— 含 MemCube / MemScheduler

**MemCube、MemScheduler 並非獨立 repo，是 MemOS 這一個 repo 內的模組**（MemCube = 統一記憶抽象單元；MemScheduler = 非同步記憶排程器，毫秒級延遲）。

- **【現況/最新版本】** GitHub `MemTensor/MemOS`，約 10.3k stars，1,971 commits，開發活躍（近期版本 v2.0.24，2026-07-19；v2.0.23，2026-07-09；v2.0.22，2026-07-03）。44 個開放 issue、42 個開放 PR，維護頻率高。研究背景：MemTensor（Shanghai）Technology Co., Ltd. 與上海交通大學、中國人民大學、**中國電信研究院**共同發表（arXiv 2505.22101）。
- **【授權】** Apache-2.0（repo 根目錄 LICENSE 確認）。
- **【可自架?】** 可以。提供 Docker Compose（MemOS API + Neo4j + Qdrant）、Uvicorn 部署、本地 SQLite 外掛（給 OpenClaw / Hermes Agent 用），文件站 https://memos-docs.openmem.net/ 。
- **【資安/授權風險】**
  - 授權本身無風險（Apache-2.0 寬鬆）。
  - **本地外掛預設開啟匿名遙測**（可 opt-out），會回傳工具名稱／延遲／版本號，官方稱不含記憶內容或個資——但預設「開」這件事，跟你們專案 CLAUDE.md 強調的「在地優先（不離地）」原則有出入，需要主動關閉才符合。
  - 團隊/論文掛名單位含中國電信研究院，屬供應鏈溯源上需留意的一點（非授權問題，是治理/資料主權考量，你們已有 cloudEmbedding 旗標 + 紅線 redactor，可視為同類風險已有對應機制）。
  - 未查到公開 CVE/安全通報，但因需搭配 Neo4j + Qdrant 兩個資料庫服務，等於多了兩個要自行硬化（鑑權、網路隔離）的攻擊面。
  - 主要語言標記為 TypeScript（58.1%），與論文/文件敘述的 Python 核心不完全一致，建議實際 clone 後確認語言分布與你們技術棧是否吃得下。
- **【建議】** 可用、活躍、授權乾淨，但**部署成本高（多一套 Neo4j+Qdrant）、預設遙測需手動關閉、來源治理需留意**。你們現有 `runner.ts` 已自建「runner core 注入 + top-k 召回 + run 結束沉澱」與 REST memory API，功能上已與 MemOS 的 MemCube/MemScheduler 概念高度重疊——**不建議整套換血**，若要借鏡，優先借「分層記憶型別（parametric/activation/plaintext）」與「排程器非同步沉澱」的設計思路即可，不必引入整個 repo 依賴。

來源：
- https://github.com/MemTensor/MemOS
- https://github.com/MemTensor/MemOS/releases
- https://memos-docs.openmem.net/
- https://arxiv.org/html/2505.22101v1

**命名混淆警示**：另有一個完全不相關的小型 repo `agiresearch/MemOS`（MIT License，僅 8 stars，是 `agiresearch/AIOS` 的分支），與 MemTensor 的 MemOS 是兩個不同專案，查資料時容易混淆，且巧合的是它的母專案也叫 AIOS——與你們公司的 AIOS 專案同名但完全無關，純屬命名巧合，勿混用。（https://github.com/agiresearch/MemOS）

## 2. Letta（原 MemGPT）

- **【現況/最新版本】** GitHub `letta-ai/letta`，約 23.9k stars，7,467 commits，最新版本 v0.16.8（2026-05-14）。26 open issues／23 open PR。官方頁面註明「Active development has moved to the Letta Agent repo」，即後續主力開發轉往 `letta-ai/letta-code`／Agent SDK，本體 repo 進入相對穩定維護階段。
- **【授權】** Apache-2.0。
- **【可自架?】** 可以，且區分清楚：本地/嵌入式執行、自架 App Server（Docker Compose 多套設定檔），或使用官方雲端 Constellation——三種模式並存,自架路徑成熟。
- **【資安/授權風險】**
  - **CVE-2025-51482**：`letta-ai/letta` 0.7.12 的 `/v1/tools/run` 端點可透過構造的 `source_code` payload 繞過 sandbox 限制，達成遠端任意程式碼執行（RCE），2025年下半年曾被記錄到主動掃描/利用。已於 PR #2630 修補，目前版本（0.16.8）遠晚於該修補點，理論上已修復，但**若你們日後自架，務必確認工具執行 sandbox 端點沒有暴露在公開網路，且版本 ≥ 修補版**。
  - 授權乾淨無虞。
- **【建議】** Letta 定位是「完整的 stateful agent 平台」而非單純記憶層，比 MemOS 更重、更接近你們整套 AIOS 想做的事（角色、工具、狀態）。若只是要記憶模組，引入 Letta 屬於過度採購；但若未來想參考「self-improving agent」設計語言，值得讀它的架構，不建議直接拿來取代你們現有引擎。自架時務必留意 CVE-2025-51482 這類「工具執行沙箱繞過」的風險類型——這正是你們 Restrictions 引擎要防的同一類問題,可當作前車之鑑。

## 3. Graphiti（Zep 的開源核心）

- **【現況/最新版本】** GitHub `getzep/graphiti`，約 29k stars（三者中最高），最新版本 v0.29.2（2026-06-08）。定位是「即時時序知識圖」（temporal Context Graph），供 LLM agent 做關係型記憶檢索，不需批次重算。
- **【授權】** Apache-2.0（LICENSE 檔確認）。
- **【可自架?】** 可以，Docker Compose 部署，後端可選 Neo4j 5.26、FalkorDB 1.1.2、Amazon Neptune、或已棄用的 Kuzu 0.11.2；LLM 端預設 OpenAI，但可換 Anthropic／Gemini／Groq——**這點對你們「在地優先」尤其重要，記得明確指向本機/自選供應商，不要留預設 OpenAI 呼叫**。
- **【資安/授權風險】**
  - **CVE-2026-32247（GHSA-gg5m-55jj-8m5g）**：0.28.1 及之前版本，`SearchFilters.node_labels` 未消毒即拼接進 Cypher 查詢，構成 Cypher Injection，CVSS 3.0 8.1（High）。特別危險之處：**在 MCP 部署情境下，可透過 prompt injection 誘導 LLM 呼叫 `search_nodes` 帶入惡意 `entity_types` 值來觸發**，屬於「LLM 代理型」攻擊面,與你們的跨模型驗證閘要防範的風險類型高度相關。已於 0.28.2 修補，目前 0.29.2 已修復。
  - **重要背景**：Zep 於 2025-04-02 官方宣布**終止 Zep Community Edition（自架版）的更新與支援**，資源全部收斂到 Graphiti 這個開源核心上。也就是說如果 WAIC 藍圖引用的是「Zep 自架版」而非 Graphiti 本身，該路徑已經死亡,只剩 Graphiti 或改用 Zep 商業雲端兩條路。
- **【建議】** 三者中 star 數最高、社群最大、授權乾淨、且「知識圖記憶」與你們現有「top-k 向量召回」是互補而非取代關係——**這是三個選型中我認為最值得列入候選的一個**，尤其如果未來要做「跨員工/跨部門的關係型記憶」（誰負責什麼、哪個技能歸屬哪個工作流），圖結構會比純向量召回更適合。但務必用 ≥0.28.2 版本，且自架時要做好 Neo4j/FalkorDB 的存取控制,避免重演 Cypher Injection。

## 總結建議（對照你們現有架構）

1. 你們在 `web os system/aios-server` 已自建的 memory 系統（runner 注入、top-k 召回、run 結束沉澱、cloudEmbedding 紅線 redactor）本質上已經是一套精簡版的「記憶 OS」，**不必為了跟上 WAIC 藍圖而整套換成 MemOS**——換入會多背兩套資料庫（Neo4j+Qdrant）、一個預設開啟的遙測、以及供應鏈治理上要多留意的背景。
2. 三個候選裡，**Graphiti 是唯一值得認真評估的外部依賴**：star 數最高、Apache-2.0、且「時序知識圖」補足你們目前 top-k 向量召回缺乏的「關係推理」能力；但要鎖 ≥0.28.2、關掉/替換預設 OpenAI 端點、資料庫存取要收緊。
3. Letta 定位是完整 agent 平台而非記憶層,不建議為了記憶功能整套導入；但它公開過的 CVE-2025-51482（工具執行沙箱繞過 RCE）值得當作你們 Restrictions 引擎設計 Shell/電腦操控限制時的參考案例。
4. 若最終還是考慮導入 MemOS，至少要做到：（a）關閉本地外掛預設遙測、（b）自架 Neo4j/Qdrant 做好網路隔離與鑑權、（c）留意其研究背景含中國電信研究院這一供應鏈治理面向是否符合你們的資安政策。

**查證侵限說明**：以上 star 數、release 日期、CVE 細節均為 2026-07-20 透過 WebSearch/WebFetch 直接查證，附上官方 repo/advisory 連結；未查到公開資料的項目（例如 MemOS 是否有正式 CVE 記錄）已明確標註「未查到」，未做推測或編造。

## 一、LangGraph
- **【現況/最新版本】** v1.2.9（2026-07-10 發布）。直接讀取 GitHub repo 頁面確認 **37.7k ★**（注意：一次 WebSearch 摘要曾誤報「126,000+ 星」，經直接 fetch 官方頁面證實為誤植/混淆自 LangChain 生態總星數，不可採信該數字）。
- **【授權】** MIT。
- **【可自架?】** 可，純函式庫（state graph 執行引擎），無強制雲端依賴；`interrupt()`/`Command(resume=)` 做 HITL，`PostgresSaver` 做生產級 checkpoint。
- **【資安/授權風險】** ⚠️ **藍圖未記載**：2025-12 至 2026-03 間揭露一條可串成 **RCE** 的漏洞鏈：
  - `GHSA-9rwj-6rc7-p77c` / CVE-2025-67644：SQLite checkpoint SQL Injection（修復於 `langgraph-checkpoint-sqlite>=3.0.1`）
  - `GHSA-g48c-2wqr-h844` / CVE-2026-28277：checkpoint msgpack 反序列化不安全（修復於 `langgraph>=1.0.10`）
  - `GHSA-mhr3-j7m5-c7c9`：BaseCache 於 msgpack 失敗時 fallback 到 `pickle.loads`，可 RCE（修復於 `langgraph-checkpoint>=4.0.0`）
  - `GHSA-wwqv-p2pp-99h5`：`JsonPlusSerializer` json 模式 RCE（修復於 `langgraph-checkpoint==3.0.0` 起加白名單）
  - 三者可串鏈：SQL injection 竄改 checkpoint 表 → 注入惡意序列化 payload → 反序列化時 RCE。**若自架且對 checkpoint store 有任何外部可寫入面（多租戶/不受信輸入），必須嚴格 pin 上述修復後版本**，這是本次查核中「比藍圖更新」的最關鍵發現。
- **【建議】** 沿用藍圖選型（MIT、可自架、認知層最成熟），但正式立項前**必須**把版本鎖定在上述修復版之後，並對 checkpoint store（SQLite/Postgres/Redis）做存取隔離，不可讓外部使用者輸入直接影響 metadata filter key。

## 五、其他值得注意的更新/糾正（回應「比 WAIC 藍圖更新或更好的替代方案」）

1. **Inngest 授權現況有變化，但結論不變**：藍圖以「SSPL 授權摩擦」淘汰 Inngest。查證後，Inngest 於 2026-01（1.0）改採「Fair Source / delayed relicensing」模式——**現在**是專有授權＋**3 年後自動轉為 Apache-2.0**的日落條款，並新增自架能力（含 Postgres 後端）。這比純 SSPL 友善一些，但**今天仍不是純 OSS**，法務摩擦本質未消除，藍圖淘汰 Inngest 的結論依然站得住，只需把理由字眼從「SSPL」更新為「fair-source 延遲轉授權，非即時 Apache-2.0」。

2. **OpenAI Agents SDK**：MIT、27k+★，仍是 pre-1.0（最新 0.17.x，週更），2026-04 起 beta 支援 subagent 模式（parent 可派生 child agent、runtime 管理平行執行/訊息路由）。這與藍圖採用其 `handoff()` 協議做設計參考的判斷一致，且 subagent 新特性剛好呼應藍圖 Delegate/Transfer 兩種語意的區分，值得追蹤但不必更動核心選型。
   來源：https://github.com/openai/openai-agents-python ｜ https://openai.github.io/openai-agents-python/

3. **Google ADK + A2A Protocol（藍圖已在 L0 治理層涵蓋，非新發現，但值得在 L2 編排比較時一併點名）**：ADK v1.0.0 已穩定（Apache-2.0，20k+★，週更）；A2A Protocol 已進 Linux Foundation 治理、spec 1.0.0/v1.0.1（Apache-2.0），官方立場「MCP 管工具呼叫、A2A 管跨組織 agent-to-agent 協商」。**若需求是跨組織/跨系統邊界的結構化交接（而非同一系統內的 agent handoff）**，A2A 是比 OpenAI Agents SDK handoff() 更對的層級選擇——這點藍圖本身其實已經正確判斷（放在 L0 而非 L2），這裡是確認其判斷正確、非新替代方案。
   來源：https://github.com/a2aproject/A2A ｜ https://google.github.io/adk-docs/a2a/

4. **沒有發現能取代 LangGraph+Temporal 雙引擎組合的更新選項**：查了 Restate、DBOS、Hatchet 等 2026 年durable execution 新秀，普遍評價是「Temporal 仍是長流程/跨服務編排最成熟選項，Restate 更輕但生態較新，DBOS 只需 Postgres 但跨服務能力較弱」，沒有證據顯示這些新專案已在人機協作+結構化交接的生產場景超越 Temporal 的成熟度。CrewAI/AG2 仍只適合對話式協作，兩份原始調查與本次查證都一致認為不可獨立當生產狀態機核心——與藍圖結論相符。

### Daytona ⚠️**重大更新,藍圖若引用需修正**

- **現況/最新版本**:v0.5.6(2026-06-10),仍是 pre-1.0、beta 階段,~5,800 星,最近一次 push 約 2026-04-26(近況趨緩)。

- **現況**:CNCF 專案,成熟穩定,OCI 相容、microVM per container。
- **授權**:Apache-2.0。
- **可自架?**:是,K8s 生態原生整合成熟。

- **資安/授權風險（重大）**：**2026-03-24 發生真實供應鏈攻擊**。攻擊者先攻陷 LiteLLM CI/CD 使用的 Trivy 資安掃描工具，取得維護者 PyPI 憑證，直接上傳兩個惡意版本 `1.82.7`、`1.82.8`（上架約 40 分鐘，多家資安廠商時間軸略有差異），內建三段式酬載：竊取 50+ 類密鑰的憑證竊取器、Kubernetes 橫向移動工具（讀取全叢集 secrets、在每個 kube-system 節點起特權 pod）、以及持久化後門（`/root/.config/sysmon/sysmon.py` + systemd service）。LiteLLM 每日下載量約 340 萬次，官方確認 1.82.6 以前版本安全，事後發布乾淨版 1.83.0、導入 CI/CD v2（隔離環境）與 cosign 簽章 Docker image，並委託 Mandiant 鑑識。另外企業版授權檢查曾誤傷非付費用戶（GitHub issue #7289、#15230），代表授權判斷邏輯還不夠成熟穩定。
  來源：https://docs.litellm.ai/blog/security-update-march-2026 ｜ https://securitylabs.datadoghq.com/articles/litellm-compromised-pypi-teampcp-supply-chain-campaign/ ｜ https://snyk.io/blog/poisoned-security-scanner-backdooring-litellm/ ｜ https://github.com/BerriAI/litellm/issues/7289
- **建議**：若 AIOS 要用它做三引擎（CLAUDE_CODE/CODEX/GROK）的路由層——核心 proxy 免費、成熟度足夠，但**務必鎖版號**（≥1.83.0，目前已到 1.93.0）、CI/CD 禁止用未鎖版的 `pip install litellm`、驗證 Docker image 的 cosign 簽章。若未來要 RBAC/審計等治理功能，需編列 Enterprise 訂閱預算，不能假設全功能免費——這點若 WAIC 藍圖只寫「開源免費」就不完整。

## 2. Portkey Gateway — 已被併購，授權出現矛盾說法

- **現況/最新版本**：這是查驗中最大的變化，很可能 WAIC 藍圖（若成文較早）沒收錄到——**2026-03 Portkey 把過去分離的企業版程式碼合併回公開 OSS repo（Gateway 2.0）**；**2026-04-30 Palo Alto Networks 宣布收購 Portkey，2026-05-29 完成收購**，現在是 PANW「Prisma AIRS」平台下的 AI Gateway 基礎設施。GitHub repo：12,482 星、228 open issues，最後 push 2026-05-25（併購前後）。
  來源：https://github.com/Portkey-ai/gateway ｜ https://www.paloaltonetworks.com/company/press/2026/palo-alto-networks-completes-acquisition-of-portkey-to-secure-ai-agents ｜ https://github.com/Portkey-AI/gateway/discussions/1576
- **授權**：**我直接抓取 repo 的 LICENSE 檔案，內容是 MIT**（Copyright 2024 Portkey, Inc），GitHub API 也判定為 MIT。但多篇二次報導（如 chatforest.com、techjacksolutions.com）宣稱 Gateway 2.0 改成 Apache 2.0——這兩者矛盾，**我沒有查到官方文件明確宣告換授權**，判斷是部分部落格報導有誤，建議部署前自行再次確認 LICENSE 檔（授權型態會直接影響你能否修改後再散布）。
- **可自架?**：可，Docker/Node.js/Kubernetes 皆可部署，且據稱 Gateway 2.0 起，circuit breaker、usage policy、MCP Gateway（OAuth 2.1）等過去要付費的功能都下放給自架用戶；雲端版保留的是 observability 儲存層、大規模語意快取、多團隊 RBAC、合規認證與企業支援。
- **資安/授權風險**：有一筆已修復的**中風險 SSRF 漏洞（GHSA-hhh5-2cvx-vmfp，對應追蹤為近似 CVE-2025-66405）**，2025-12-01 公告：`x-portkey-custom-host` 這個 request header 未驗證就被信任，可被利用讓 gateway 對內網任意主機（包括雲端 metadata 端點如 AWS 169.254.169.254）發請求，屬於典型 SSRF。另一個結構性風險是**被 PANW 收購後的路線圖不確定性**——開源承諾是否持續、未來新功能是否會綁進 Prisma AIRS 商業套件，目前無官方明文保證，只能觀察後續 release 節奏。
  來源：https://github.com/Portkey-AI/gateway/security
- **建議**：技術上可用，但現階段**不建議把它當長期戰略依賴**——授權敘述本身有矛盾待官方澄清，且剛被大型資安廠商收購，路線圖有變動風險。若只是短期測試路由能力可以用，正式導入前務必盯緊接下來 2-3 個月的 release note。

## 3. OpenRouter — 非開源，無法自架，屬託管服務

- **現況**：查驗時點運作正常，但過去 8 個月內至少 3 次中斷（2025-08-28 資料庫中斷 50 分；2026-02-17／02-19 快取層連環故障，2/19 造成 35 分完全中斷），且**無正式 SLA、無停機賠償**，錯誤處理曾把基礎設施故障誤報成 401「User not found」（已修正為 503）。
  來源：https://openrouter.ai/announcements/openrouter-outages-on-february-17-and-19-2026 ｜ https://status.openrouter.ai/
- **授權**：**非開源，屬託管專有服務**。條款（ToS）明訂所有服務相關智慧財產權歸其運營主體（法律文件上寫的是 Peekaboo Game Limited）所有，使用者僅保留自己輸入內容的著作權，輸出內容的權利依各模型的 Model Terms 而定。**沒有查到任何官方聲明表示 OpenRouter 本體是開源或可自架**——這點需要糾正藍圖若把它跟 LiteLLM/Portkey 並列為「同級開源選項」的話，OpenRouter 本質不同（它是聚合路由服務，不是你能部署的軟體）。
  來源：https://openrouter.ai/terms
- **可自架?**：**不可**。所有請求都經過 OpenRouter 自家伺服器轉發，沒有 self-host 選項。
- **BYOK 資安/授權風險**：OpenRouter 的 BYOK 讓你用自己的供應商金鑰路由，金鑰宣稱加密儲存，且 2026-10-01 起每月提供 100 萬次免費 BYOK 請求；但**BYOK 不代表資料不經過 OpenRouter 基礎設施**——prompt 仍會先進到 OpenRouter 伺服器再轉發給實際供應商，只是計費/金鑰換成你自己的。另一個常被忽略的風險：**若啟用成本導向路由，預設模型清單包含中國託管模型（DeepSeek、阿里 Qwen、Moonshot AI）**，資料可能未經明顯提示就被路由到杭州的伺服器，若記錄（logging）未關閉，你留存的 prompt/chat 內容甚至可能被取得「不可撤銷的商業使用權」。這對 AIOS「在地優先、不離地」的核心設計原則是直接衝突點，需要特別留意。
  來源：https://openrouter.ai/docs/guides/overview/auth/byok ｜ https://www.layer3labs.io/guides/openrouter-explained
- **建議**：OpenRouter 適合快速原型驗證模型選擇，**不適合當作 AIOS 正式生產路由層**——一是它違反本機優先/資料不落地的專案原則，二是無 SLA、無法自架，三是預設路由可能繞到中國模型，資安/合規風險偏高。若要用，務必強制關閉 prompt logging、白名單模型供應商（排除自動導向中國託管模型）。

## 小結建議（給 AIOS 決策參考）

1. **LiteLLM 仍是最成熟的自架選項**，但 2026-03 供應鏈攻擊是實打實發生過的事件，導入前必須鎖版號、驗證簽章，不能當作「無腦拉最新版」的依賴。

4. **Bifrost（Apache 2.0、Go、效能更好、授權單一無爭議）與 Envoy AI Gateway（CNCF 中立治理、v1.0 剛發布）是兩個值得取代或並列評估的更新選項**，尤其 Envoy AI Gateway 的基金會治理模式，能規避「單一公司被收購導致路線圖突變」的風險——這正是 Portkey 案例示範的教訓。

## 1. AG-UI Protocol（ag-ui-protocol/ag-ui）

- **現況/最新版本**：活躍開發中，最新 release 標示為 2026-07-15；star 14.8k、fork 1.3k、被 101 個專案引用。已被 CopilotKit、LangGraph、CrewAI、Mastra、Pydantic AI、Agno 等框架整合，Microsoft／Google／AWS／Oracle 文件中亦有提及。治理為 CopilotKit 主導的社群工作小組（雙週會），**未**進入 Linux Foundation 等中立基金會。
- **授權**：MIT。
- **可自架？**：是——純協議規格＋SDK，前後端皆為 library，無中央服務依賴。
- **資安/授權風險**：授權風險低（MIT 寬鬆）。主要風險是治理仍由單一商業公司（CopilotKit）主導，尚未如 MCP／A2A 般進入中立基金會，長期路線圖有被廠商牽引之虞；協議本身不處理使用者資料，風險多落在下游 Runtime 實作。
- **建議**：與貴專案（WAIC 藍圖）既定判斷一致——AG-UI 作為北向協議、CopilotKit/assistant-ui 僅作可替換 adapter，不讓其 Runtime 變成 source of truth。此判斷在今日查核下仍成立，無新變數。

## 2. Model Context Protocol（協議本身＋官方 Registry）

- **現況/最新版本**：現行穩定規格為 `2025-11-25`；下一版 `2026-07-28` 規格**即將在 8 天後定案發布**（RC 已於 2026-05-21 定案，10 週驗證期），內含**破壞性變更**：拿掉 `initialize`/`Mcp-Session-Id` 握手改為完全 stateless core、Tasks 由核心畢業為 Extension、新增 **MCP Apps**（伺服器可直接送出在 sandboxed iframe 渲染的 HTML 介面）、6 項 SEP 強化 OAuth2/OIDC 對齊、正式 Deprecation Policy（12 個月週期）。
  官方 **Registry**（modelcontextprotocol/registry）自 2025-09-08 上線 preview 至今（2026-07-20）**仍處於 API v0.1 freeze/preview、未 GA**，由獨立的 Registry Working Group（4 人）運作，非 AAIF 直接治理。
- **授權**：程式碼/規格 Apache-2.0（有例外條款）；文件（非規格）CC BY 4.0；Registry 新程式碼 Apache-2.0、舊程式碼 relicense 為 MIT（混合授權）。
- **可自架？**：是，協議與 Registry 皆可自架；但 7/28 的破壞性變更需要提前規劃遷移。
- **資安/授權風險（嚴重，且是本次查證中比藍圖記載更嚴峻的部分）**：
  - **架構級 RCE 設計缺陷**：The Register（2026-04-16）與 The Hacker News 報導，MCP 的 **STDIO 傳輸機制**允許任意 OS command execution，影響約 **20 萬台伺服器、1.5 億以上下載量**的下游套件，已知 10 餘個 CVE（GPT Researcher CVE-2025-65720、Upsonic CVE-2026-30625、Windsurf CVE-2026-30615、LiteLLM CVE-2026-30623、DocsGPT CVE-2026-26015、Flowise GHSA-c9gw-hvqq-f33r 等）。**Anthropic 官方回應是「此為預期行為」，拒絕修改協議架構**，僅更新安全指引；研究者認為「這個改動什麼都沒修好」。
  - **Registry 毒化實測**：OX Security（2026-04-15）測試 11 個 MCP registry，**9 個成功被塞入 PoC 惡意套件**。
  - **真實入侵案例**：2026-02，SmartLoader 集團用至少 5 個偽造 GitHub 帳號 fork 並上架惡意版 Oura Ring MCP server 到正規 registry，夾帶 StealC infostealer 竊取瀏覽器密碼、雲端 token、加密錢包。
- **建議**：這些是**藍圖已定案方向（「MCP 只定義 mechanism 不含 policy，治理靠自建 Gateway 層」）的實證，且優先度應由「建議」升級為「上線前必須完成的阻斷項」**：(1) 絕不對不可信輸入直接暴露 STDIO transport；(2) 絕不從 Official/Public Registry 直接 auto-run 第三方 server，必須經 internal curated registry（digest pinning + SBOM + 來源驗證）；(3) 追蹤 7/28 新規格遷移視窗；(4) 若採用 MCP Apps，其 sandboxed iframe 渲染邏輯需與藍圖既有的 Sandboxed Renderer Isolation 設計比對，避免重工或安全模型衝突。

## 3. A2A Protocol / Agent Card（Linux Foundation）

- **現況/最新版本**：spec v1.0（2026-04）／GitHub release 約 v1.0.1，官方 SDK 涵蓋 Python/JS/Java/Go/.NET（部分報導含 Rust）。2026-04-09 一週年公告：**150+ 生產組織支援、22,000+ GitHub star**；同月新增 **Agent Payments Protocol (AP2)**、簽章 Agent Card、Microsoft Copilot Studio／Azure AI Foundry／Amazon Bedrock AgentCore GA 整合。
- **授權**：Apache-2.0。
- **治理**：**Linux Foundation 直接治理**（2025-06-23 由 Google 捐贈接手），與 MCP 走的是 LF 大帽子下**不同軌道**——A2A 是 LF 自己的獨立 project，不在本次新設的 AAIF directed fund 內。
- **可自架？**：是，協議規格與官方 SDK 全開源，Agent Card 為靜態 JSON，發布於 `/.well-known/agent-card.json`（遵循 RFC 8615），client/server 皆可自架、無中央依賴。
- **資安/授權風險**：相對 MCP 低（設計上是 opaque cross-process 邊界而非直接 command execution）。「150+ supporting organizations」屬**生態層級宣稱**、非 production 部署量證據（藍圖已正確提醒此點，本次查證亦未找到具體 production throughput/故障率數字可補充）。既然已有 signed Agent Card 機制，若未強制驗證簽章，仍有被偽造 Agent Card 導向惡意 endpoint 的風險。
- **建議**：與藍圖定案一致（A2A 僅用於跨組織 opaque 邊界，內部子 agent 不必強迫走 A2A）。可補強一點：在 L0 Agent Registry 設計中把「Agent Card 簽章驗證」列為**必要**而非可選項。

## 比 WAIC 藍圖（`WAIC_2026_參展報告_v2_開發藍圖.html`）更新或更完整的發現

我對照了貴專案該份藍圖文件（已於今日 2026-07-20 完成兩來源查核），發現以下**藍圖沒有捕捉到、但屬於同一查核日應該補上**的資訊：

1. **MCP 治理層級比藍圖記載的更完整、更中立（好消息）**：藍圖只提到 MCP Registry 有獨立 Registry Working Group，但**沒提到 MCP 協議整體**已於 2025-12-09 由 Anthropic 捐入 Linux Foundation 旗下新設的 **Agentic AI Foundation (AAIF)**，OpenAI/Block 為共同創辦者，AWS/Google/Microsoft/Cloudflare/GitHub/Bloomberg 為 Platinum members，2026-02-24 已選出首任治理主席（David Nalley，前 Apache Software Foundation 總裁），會員數達 146。這代表 MCP 協議整體的中立性/公信力比藍圖評估的更高，可以更放心採用官方規格作為長期依賴。
2. **資安層面有藍圖未捕捉到的重大且具體的惡化證據**：藍圖的供應鏈風險提示停留在原則層級（「Formal.ai MCP 權限陷阱案例」一筆），本次查到的是 2026 上半年才浮現、**更嚴重且已有官方拒絕修復立場**的具體事件——MCP STDIO 架構級 RCE 缺陷（20 萬伺服器/1.5 億下載/10+CVE，Anthropic 明確拒絕修改協議）、OX Security 的 registry 實測 9/11 被毒化、SmartLoader 真實入侵案例。這些應該讓藍圖既有的 Gateway/policy engine 強制關卡的優先度，從「建議做法」提升為「上線前必須完成的硬性阻斷項」。
3. **即將發布的 MCP `2026-07-28` 新規格**（僅剩約一週）帶有破壞性變更，其中新增的 **MCP Apps**（伺服器端可送出 sandboxed iframe 渲染的 HTML 介面）與藍圖 L1 互動層自建的「Sandboxed Renderer Isolation」/AG-UI 協議在概念上有重疊。建議先觀察其成熟度，暫不急著採用，但需追蹤是否與既有設計衝突或可互補。
4. **沒有找到能取代藍圖既定選型的更新/更成熟替代方案**——本次查證再次確認：AG-UI 在事件協議層仍是唯一廠商中立的成熟選項；A2A 在跨代理層仍是 Linux Foundation 治理下唯一成熟標準；ContextForge 在 MCP Gateway 層仍是功能最完整、確定 GA 的自架選項。因此**建議維持藍圖既有選型，不需換選型**，只需要：(a) 補強 MCP Registry/Gateway 的強制 admission gate、(b) 追蹤 7/28 規格遷移、(c) 在 Agent Registry 設計中把 A2A signed Agent Card 驗證列為必要項。
