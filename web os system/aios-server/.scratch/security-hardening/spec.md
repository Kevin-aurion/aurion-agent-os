# Spec — 安全強化與治理修正（Code Review 後續）

> 來源：mattpocock `code-review` skill 對 AIOS 全系統掃描的 findings。以 `to-spec` 綜合產出（無訪談）。
> 狀態：ready-for-agent

## Problem Statement

系統剛完成一輪大規模開發（P0/P1/P2 + 整合），但 code review 揭露幾個會實際傷害使用者的缺陷：

1. 上傳惡意 zip 技能包，可以把檔案寫到主機任意可寫路徑（後端跑在主機、非容器內）。
2. 把員工「部門」取名成 `..`，具現化員工時會把檔案寫出 `MyAgent/` 之外。
3. 用中文命名技能／員工時，slug 會退化成空字串或殘餘英文（例：「每日帳款掃描」→ `""`、「發票輸入ERP」→ `erp`），造成命名衝突與難以辨識的資料夾。
4. 高風險員工若掛在「耐久（durable）」工作流上，會永久卡死等一個沒人送的核准信號；同時耐久路徑用一個假字串就繞過了核准閘 —— 治理形同虛設。
5. 耐久工作流回傳的結果缺欄位，關鍵字觸發時使用者在聊天只看到「(no output)」。
6. 記憶 embedding 在資料庫查詢失敗時，會**預設把內容送去雲端**（fail-open），與「資料不離地」的產品承諾相衝突。

## Solution

以「安全與治理是硬約束」為原則，逐項改成 fail-closed：

- 任何接受使用者可控路徑／檔名／zip entry 的地方，一律走同一個「路徑必須留在根目錄內」的守門函式。
- 中文命名要能產生穩定、可辨識、不衝突的 slug。
- 「耐久 + 高風險」這個會卡死又會繞過治理的組合，直接拒絕（而不是讓它靜默壞掉）；假核准字串的後門移除。
- 耐久路徑回傳完整執行結果，聊天看得到真正輸出。
- 記憶 embedding 在任何不確定情況下，選擇「不送出」。雲端 embedding 本身是老闆明確要的設計（OpenRouter Gemini），但必須是**明示的選擇**，不是失敗後的預設。

## User Stories

1. 作為系統管理者，我要上傳的技能 zip 只能寫進該技能自己的資料夾，這樣惡意壓縮檔就無法覆寫我主機上的其他檔案。
2. 作為系統管理者，我要 zip 內含 `../` 或絕對路徑的項目被明確拒絕並回報錯誤，這樣我知道這個包有問題。
3. 作為訓練師，我要把員工部門命名成任何文字都不會寫出員工工作區之外，這樣不會意外汙染專案目錄。
4. 作為訓練師，我要用中文命名技能（例如「每日帳款掃描」）也能得到一個穩定、看得懂、不重複的 slug，這樣我在檔案系統與清單裡找得到它。
5. 作為訓練師，我要中文命名不會產生空字串 slug，這樣不會出現無法辨識或互相衝突的資料夾。
6. 作為老闆，我不要有任何「假核准」能繞過高風險員工的人工核准閘，這樣治理是真的。
7. 作為老闆，我要系統在我把高風險員工配到耐久工作流時明確擋下並告訴我原因，而不是讓那個執行永久卡住。
8. 作為使用者，我用關鍵字觸發耐久工作流時，要能在聊天看到真正的執行輸出，而不是「(no output)」。
9. 作為老闆，我要記憶 embedding 在資料庫失敗時選擇「不送雲端」，這樣「不離地」承諾不會被一個 catch 破壞。
10. 作為老闆，我要文件明載「雲端 embedding 是刻意的例外（OpenRouter Gemini）」，這樣團隊知道邊界在哪、不是意外。
11. 作為開發者，我要三引擎（Claude/Codex/Grok）的派工邏輯收斂成單一對照表，這樣新增引擎或修改行為時不會漏掉某個分支。
12. 作為開發者，我要「決策」路徑也支援 GROK，這樣 GROK 員工不會被靜默改用 Claude 執行、成本也不會記錯帳。
13. 作為維運者，我要這些修正都有測試佐證，這樣我信得過它們真的擋住了。

## Implementation Decisions

- **新增共用路徑守門模組**：提供「把候選路徑 resolve 後，斷言它仍在指定根目錄內」的函式，以及安全的路徑組合與單一路徑片段清洗。既有的 `readWikiFile` 已是正確典範（resolve + `startsWith(root + sep)`），新模組把它抽成全站共用。所有接受外部輸入路徑的呼叫點改走它。
- **新增共用 slug 模組**：slug 保留 CJK 字元（不再被 `[^a-z0-9]` 清空），英數照舊小寫化，長度上限維持；若結果為空則退回一個穩定的簡短雜湊，永不回傳空字串。全站 slug 產生改用它（目前有 5 份重複實作）。
- **部門清洗**：除既有非法字元外，剔除純點號片段；並在算出員工目錄後斷言它位於員工根目錄內，否則拒絕具現化。
- **zip 解壓**：每個 entry 名稱先清洗＋斷言在技能根目錄內，含 `..`／絕對路徑／磁碟機前綴者拒絕整包並回報。
- **治理閘**：核准判定不得只看「有沒有傳一個字串」——耐久路徑不得再自行偽造核准識別碼。「耐久 + 高風險」組合在工作流建立／啟用與派工時一律拒絕，錯誤訊息說明原因（此組合的真正 HITL 串接列為未來工作）。
- **耐久回傳**：耐久工作流回傳完整的執行結果形狀（含步驟結果與輸出），呼叫端不再做不安全型別轉換。
- **記憶 embedding**：查詢限制失敗時回「不允許」（fail-closed）。雲端 embedding 預設維持啟用（老闆明確要 OpenRouter Gemini），但於文件明載為刻意例外。
- **引擎派工**：把 execute／verify／decide 三處 if-cascade 收斂成單一引擎對照表（每個引擎一組行為），decide 補上 GROK。

## Testing Decisions

- 好的測試只驗**外部行為**：給一個惡意輸入，斷言它被拒絕且檔案沒被寫出去；給中文名稱，斷言得到非空且穩定的 slug。不測內部實作細節。
- 受測模組：路徑守門、slug、部門清洗、zip 上傳、核准判定、耐久回傳形狀、embedding 允許判定。
- 既有測試典範：本輪開發都採「臨時 `.ts` 腳本 + `tsx` 實跑 + 真 DB 讀寫 + 用完清理」，沿用此模式；安全項一律加**負向測試**（惡意輸入必須失敗）。
- 每一項改動後跑 `tsc --noEmit` 與 `npm run build`，並確認跨模型驗證閘、紅線 redactor 行為零回歸。

## Out of Scope

- 為「耐久 + 高風險」串接完整的 durable HITL 核准 UI／路由（本次僅擋掉該組合）。
- 把 embedding 改為完全本地模型（老闆已指定 OpenRouter）。
- `SkillVersion` / `Workflow.durable` / 身分卡 等既有 lib 的 REST 端點開放（schema 超前 API 的落差清單另案）。
- Channel enum 的 TELEGRAM/SLACK/DISCORD 實作。

## Further Notes

- 部分要改的檔案帶有老闆未提交的 WIP（技能與員工路由、技能建置、員工組裝）。修正要**外科手術式最小改動**，且提交時不可把 WIP 的無關變更一起帶走。
- 三引擎派工收斂屬「寬幅重構」：先擴充（新對照表與舊分支並存）再逐步遷移，保持每步可編譯。
