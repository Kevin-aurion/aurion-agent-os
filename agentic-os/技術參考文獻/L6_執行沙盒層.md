# L6 L6 執行沙盒層（Firecracker/E2B 自架、隔離技術比較、snapshot）

**策略**：🟧多後端混合（🧠借用10／💰採購2／📚文獻64／⚠️缺口11）。定案：Firecracker（Apache-2.0）為預設 microVM——AWS Lambda 生產驗證、開銷最小；GPU 工作負載走 Kata＋Cloud Hypervisor/QEMU（Firecracker GPU 僅 Developer Preview）；無 nested-virt 環境以 gVisor 備援；確定性小工具用 Wasmtime 降 TCB。借 E2B 的 SDK/API 介面、envd 協定與 snapshot 流程設計（唯一把 snapshot/resume 做成完整開源實作的），但其排程層依賴 BSL 授權的 Nomad/Consul——排程器自研（或評估 K8s 原生）。核心槓桿：resume 預熱快照而非冷啟動，本地 NVMe＋COW rootfs；SLO 分 create/resume/ready 三段量測。

## 💰 需採購 / 外部授權

- 具nested virtualization或bare-metal存取能力的運算容量（自有實體伺服器或雲端裸機/nested-virt機型）：Firecracker/Kata/Cloud Hypervisor都需要/dev/kvm存取，可行路徑為AWS bare-metal(.metal)或2026-02後開放nested virt的C8i/M8i/R8i機型、GCP限Intel VT-x/Haswell以上並排除E2/memory-optimized/AMD/Arm/H4D、或自有實體裸機；Azure兩來源均查無官方對Linux KVM/Firecracker的production support承諾。延遲敏感的production仍建議bare-metal而非nested-virt雲端實例。
- GPU硬體（供Kata+Cloud Hypervisor/QEMU的GPU sandbox pool使用）：GPU passthrough/vGPU/MIG需要實體GPU卡與對應driver/firmware支援，Firecracker上游GPU仍屬Developer Preview/PoC不建議生產使用；兩來源均未討論NVIDIA vGPU/GRID等虛擬化授權費用，需另外查證商業採購限制。

## 🏗️ 自研開發 Spec

自研核心含 Sandbox Control API（北向REST/gRPC，idempotency key、X-API-Key）、Host Orchestrator daemon（每host管理Firecracker/Kata process、jailer、netns/TAP、snapshot本地cache、UFFD/NBD）、Template Builder service（Dockerfile→rootfs→provision→envd→readiness probe→pause→snapshot→artifact）、Guest Agent（envd-equivalent，Connect RPC，短效token）、Client Proxy/Edge Router（依sandboxId路由、auto-resume）、Snapshot & Artifact Store（S3-compatible，digest驗證）、Network Policy Engine（per-sandbox netns+TAP+nftables/eBPF、default-deny、自建DNS resolver防rebinding）、Postgres metadata store、Redis/等效KV(routing真相源，需查證必要性)、Coordination/IPAM store、Scheduler（snapshot-locality-aware，避免依賴BSL的Nomad）、Multi-backend Runtime Abstraction Layer、Identity Reinjection module（每次resume重設MAC/IP/vsock CID/machine-id/SSH host key/token/PRNG）、Browser Sandbox Gateway（獨立microVM、CDP僅綁127.0.0.1）、OTel Metrics pipeline、Lifecycle Event Bus（Postgres outbox+NATS/JetStream）。核心資料模型：SandboxState列舉、Template/Sandbox/Snapshot/NetworkPolicy實體（皆版本化不可變）、Prefetch manifest。Firecracker REST API僅綁Unix domain socket，Restore critical path須平行化，優先host-side COW rootfs。

## ❌ 反模式（要避免）

- Firecracker REST API不可對外綁TCP，只能用Unix domain socket——對外暴露等同讓任何能連到host網路的人直接控制VM
- 不可讓object storage/IPAM查詢卡在snapshot restore的critical path——必須靠local NVMe cache與預先分配好的網路資源，否則百毫秒級resume目標無法達成
- 不可假設TCP/WebSocket/PTY連線能跨越snapshot restore存活——SDK/client必須自行處理reconnect邏輯
- 同一snapshot被多個VM resume時，不可延用原本的MAC/IP/vsock CID/machine-id/SSH host key/token/PRNG狀態——會造成熵重複與身分碰撞，須在guest agent啟動前完成reinjection
- 不可把部落格/廠商行銷宣稱的延遲數字（如dev.to的『28ms restore』、Kata『~150-300ms』、E2B行銷頁『5-30ms』）當成可承諾的SLA——只有CI強制的官方Firecracker SPECIFICATION.md數字（≤125ms boot、<5MiB overhead、≤150 microVM/s）可信
- 不可預設整套沿用E2B的Nomad＋Consul排程層而不做授權審查——Nomad/Consul為BSL授權而非Apache-2.0，需自研排程器或另尋替代，只借用E2B的API/協定設計
- 不可把Firecracker當作GPU workload的執行後端——上游GPU passthrough仍是Developer Preview/PoC，GPU workload需獨立走Kata+Cloud Hypervisor/QEMU的pool
- restore敏感的host不建議用cgroup v1——會拖慢restore速度，建議採用cgroup v2
- template snapshot建立前不可留有secret/cookie——build階段預熱的process與browser profile都要在snapshot前清除機敏資料
- domain-based egress allowlist不可假設涵蓋QUIC/HTTP3——SNI/Host檢查只看得到TCP上的HTTP(S)，必須額外處理UDP/443或QUIC流量，否則policy形同虛設
- 不可把E2B的BYOC模式當成『完全self-host』——BYOC下E2B cloud仍管理部分lifecycle並收集匿名metrics
- 不可省略snapshot前的quiesce（fsfreeze/sync）步驟——直接pause+snapshot可能讓restore後的檔案系統處於不一致狀態
- 不建議用外部託管瀏覽器服務（third-party managed browser API）作為主要browser sandbox方案——違反自架原則，僅列為備援選項

## ⚠️ 查證缺口（誠實標注）

- AWS self-host成熟度矛盾：Grok指出E2B官方文件將AWS self-host標示為Beta（GCP才是『完整』支援），Codex描述的AWS預設node pool配置卻讀起來像production等級，未提及beta警語，需直接查e2b-dev/infra現版文件確認
- Nomad/Consul的BSL授權疑慮僅Grok提出：若『license友善』是硬性要求，需法務審查BSL條款可接受度，目前無validated的Apache-licensed排程器可直接取代
- Wasmtime冷啟動數字差兩三個數量級：Codex稱pooling allocator下instantiate約5µs，Grok稱冷啟動約1-3ms(二級來源)，需自行controlled benchmark後才能寫入SLO
- Snapshot restore端到端延遲兩來源數字對不上，且尚無可承諾的SLO：Codex的NumaVM第三方實測176ms(snapshot load子步驟25ms)並草擬P50≤150ms/P95≤300ms/P99≤500ms；Grok引用dev.to『~28ms restore』，兩者『restore』定義範圍可能不同，需先定義量測範圍再重新量測
- Kata Containers開機延遲無官方數字：Codex只找到記憶體開銷數字(非開機時間)，Grok只找到部落格~150-300ms估計，衡量指標不同，需在選定VMM backend上自行benchmark
- 逃逸機率/安全事件量化數字：兩來源都明確查無任何runtime的量化風險數字，安全比較目前只能停留在質化推理，需靠自己紅隊測試補上
- E2B對Azure/通用Linux bare-metal self-host的支援：兩來源一致同意目前不支援，但都沒查到官方路徑圖或porting工作量估計
- Redis是否為E2B架構必要元件：Grok列為核心元件，Codex完全沒提到，需直接查e2b-dev/infra原始碼確認
- 多項具體版本號/port號僅單一來源提供，未交叉驗證（如Firecracker 1.14.1、guest Linux 6.1 kernel、envd相關port號等），開工前必須重新對照當下原始碼版本確認
- GPU sandbox pool的商業/授權成本：兩來源都只討論技術可行性，完全沒有討論NVIDIA vGPU/GRID等虛擬化授權費用
- E2B domain-based egress filtering對QUIC/HTTP3的處理：兩來源都確認這是已知漏洞點，但都沒說明具體解法
