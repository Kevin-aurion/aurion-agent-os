# 給 Kevin 的誠實評估

你問的核心是：「我是不是被上海帶偏、忽略了原本更好的設計？」直說——**沒有帶偏，但你踩在一條容易帶偏的路上，得靠紀律守住。** 以下就事論事。

## 一、你哪裡想對了、哪裡要修正

**想對的：**
- 用 L0–L9 十層去做全棧盤點，這個框架本身是對的——它逼你把「治理、成本、沙盒、文件解析、計費」這些你原本沒系統性想過的層攤開來看。你確實因此發現了真缺口（成本盲區、沙盒全有全無、讀不了 PDF）。
- 你願意借開源、不硬造輪子，方向對。
- 最重要的：你**自己先做了即時查驗過濾**（AGPL 感染、BSL/ELv2、MinIO 封存、LiteLLM 供應鏈、MCP RCE、MemOS 遙測），沒有把藍圖當聖經照抄。這一步救了你——尤其「記憶別換 MemOS」「不上 LiteLLM proxy」這兩個判斷是對的，是即時查驗直接背書的。

**要修正的：**
- 別把「借上海骨架」在心裡偷換成「我的東西不夠好、要換血」。事實相反：你在 **L2（驗證閘）、L3（技能閘）、L4（記憶+紅線）** 這三層的設計，比上海藍圖更硬、更貼在地治理。上海的 Outcome Judge「獨立於執行者」講了半天，你的跨模型驗證閘早就在 `compileManifest` 載入時強制 execute≠verify、還有 fail-closed 的 `isApproved`——**你已經做到了他們在講的東西，而且更早、更硬。** 修正點就是：這三層**只准強化、不准為了「長得像上海」而弱化**。
- 你的焦慮該轉向：不是「我是不是不夠像他們」，而是「我這三個致命硬約束缺口（成本、shell/sendEmail、HITL）為什麼還沒補」。那才是真正在流血的地方。

## 二、上海藍圖的可信度與風險

老實講：**上海藍圖是一份「最佳實踐願望清單」，不是一份「經過驗證的架構」。** 它列的很多東西是文宣或 GA 宣稱，不等於能安全落地。具體風險：
- **MCP**：有架構級 RCE（STDIO transport，Anthropic 稱「預期行為」拒改）、10+ CVE、registry 毒化事件。藍圖把 MCP 當事實標準沒錯，但「治理必須自建 gateway」這句才是重點——不能從 public registry auto-run。你 aios-mcp 選擇「當 server 供給」而非「消費外部」，反而避開了最大的雷，這判斷是對的。
- **沙盒**：Firecracker/E2B 需要 `/dev/kvm`（Linux）或 GCP/AWS 帳號，跟你 macOS 在地優先**直接衝突**。照搬會把你拖進雲依賴，違背你的核心賣點。取其「小房間」原則、不取其本體，是對的。
- **授權地雷**：Lago 是 AGPL-3.0、MinerU 2026-04 起改自訂 license、Graphiti 預設打 OpenAI endpoint、Unleash 授權來源矛盾。這些藍圖不會替你把關，法務得一個個過。
- **一句話**：上海的價值是「幫你看到缺口」，不是「給你可抄的答案」。你已經在做正確的過濾，繼續保持懷疑。

## 三、務必保留的護城河 vs 務必補的缺口

**護城河（打死不弱化）：**
1. 跨模型驗證閘——載入時強制 executor≠verifier、fail-closed 決定性 oracle、驗證器跨回合續命。這是 crown jewel，比上海單模型 LLM-as-judge 硬一個量級。
2. 在地優先、無 key passthrough——引擎用你自己的 CLI 授權，**天然免疫 LiteLLM 那類 gateway 供應鏈攻擊**。這是被動送你的安全優勢。
3. 引擎層限制（webSearch/computerUse/cloudWrite/cloudEmbedding 真的在 CLI flag/程式碼層攔截）。
4. 紅線 redactor 永遠生效，不受任何旗標影響。
5. understand→confirm 技能閘（跨模型審查 + 靜態 lint + 人審才掛載）。

**缺口（在流血，依序）：**
- **P0-1 成本＝0**（L7）：引擎呼叫完全無 token/成本追蹤，已經釀成「刷到幾個億」的真實事故。這是最高優先，不是之一。
- **P0-2 shell 預設開 + sendEmail 只有提示文字**（L0/L6）：不聽話的模型可以繞過。這直接違反你自己的第一性原則「安全必須是硬約束，不能靠模型自覺」。
- **P0-3 HITL 是死狀態**（L2）：`AWAITING_REVIEW` 定義在 schema 裡，但**全庫沒有一行程式碼把 run 設成這個狀態**。法規紅線/高風險動作現在無處可暫停。
- P1：稽核鏈可被 DB 管理員竄改、無耐久執行（crash 不能 resume）、沙盒全有全無、讀不了文件、只有計數沒有燈號。

## 四、對「一個 workflow 就能重構完 L0–L9」的預期管理

直說：**不可能，別這樣想，也別這樣對外承諾。**

- L0–L9 全棧重構是**跨多個季度的工程**，不是一個 workflow、一次對話能收尾的。上海那份藍圖背後對應的是一整個園區、多個團隊的東西。
- 一個 workflow（也就是這一輪）能實際交付的是兩件事：**（a）這份融合版 Spec（策略對齊，已完成）；（b）P0 三項止血**——成本帳本、shell/sendEmail 硬攔截、HITL 復活。這三項全都能在現有 `runner.ts / restrictions.ts / dashboard.ts / AuditLog` 上**增量補齊，不需推翻架構**，這是好消息。
- 之後 P1/P2 要按波次排，每一波都走你自己定的「Grok 寫、Opus 審、實跑證據才過」迴圈。別想一口氣吃完。
- 最務實的心態：**這不是「重構」，是「在一個已經比你以為的更強的地基上，補三個會出人命的洞，然後分季度長肌肉」。** 你的地基（L2/L3/L4）沒問題，別自己嚇自己。
