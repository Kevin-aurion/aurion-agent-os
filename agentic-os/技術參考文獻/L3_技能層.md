## 🏗️ 自研開發 Spec

Skill Discovery/Resolver/Loader 依 Progressive Disclosure（L1 metadata→L2 SKILL.md 本文→L3 scripts/references/assets）分層載入，L3 預設 lazy load 且於 sandbox 執行；Trust & Permission Policy Engine 比對 manifest 宣告 permissions 與實際行為 diff，決定是否觸發 human approval 或 sandbox 隔離執行；Registry & Content Store 採 SHA-256 content-addressed storage+channel pointer（stable/canary/latest），rollback=切換指標而非覆寫內容；Promotion Controller 管理 candidate→sandbox eval→human review→immutable release→canary→stable 狀態機；Distiller/Auto-capture Pipeline（Trace→隱私過濾→outcome grading→clustering→workflow abstraction→candidate 合成→sandbox replay→eval gate→human review 佇列）只產生 candidate，不具 production 發佈權。核心資料模型：SKILL.md frontmatter（規格內建，不可任意擴充頂層欄位）、skill.manifest.json（自訂：schemaVersion/contentDigest/dependencies/permissions/eval/provenance）、版本三層拆分（Human semver/Content hash/Registry revision，各自獨立比對）、SkillEvalSuite/evals.json、Trace record（以 OTel GenAI semantic conventions 為底）、Registry metadata schema（immutable publication）、Candidate skill record（與 production skill 分開儲存）。

## ❌ 反模式（要避免）

- 把 version 當作 SKILL.md frontmatter 正式欄位直接使用——規格未定義此欄位，應放 manifest 或 metadata
- 在 frontmatter metadata 塞入 nested JSON/物件——規格規定 metadata 值須為 string
- 讓 production agent 直接改寫或覆寫既有已發佈 skill——自動沉澱必須先產出 candidate，經 sandbox eval+human review 才能 promote
- Eager-load 所有 skill 的完整 SKILL.md 本文——違反 progressive disclosure，理論上可能吃掉近 100,000 tokens
- 把 MCP Registry 當作 skill registry 使用，或將兩者資料模型混為一談——MCP Registry 只登錄 server metadata，不具備 skill 的 permission/eval/provenance 語意
- 只鎖 MCP server 名稱而不鎖 version+schemaDigest+capabilities——server 行為或 schema 變更會 silently 破壞已發佈的 skill
- 直接 fork/vendor 授權不明或有爭議的專案程式碼——如本次調查中兩來源對 AWM 授權判斷矛盾，應先查清楚 license 再決定是否整合
- 選用平台限制重的元件作核心自架依賴而未評估替代方案——如 ELv2 的 Phoenix、綁定 Convex/OpenAI embedding 的 ClawHub 後端、或需要重量級硬體的 Braintrust self-host 規格
- 把第三方/使用者提交的 skill 當作純文字內容而非可執行程式碼——skill 本質是 markdown+script，等同可執行安裝檔，缺乏 sandbox/permission diff/簽章即上架已被資安研究點名為攻擊面
- 用覆寫舊版內容的方式實作 rollback，而非 content-addressed store+pointer 切換——覆寫會破壞不可變性與可追溯性
- 允許 registry 在發佈後對同一 version 改內容或改 metadata——破壞 immutable publication 保證，下游 lockfile/pin 機制會失真
- 各元件（trace-collector/eval-runner/distiller）各自定義 trace/eval schema 而不對齊共用標準（如 OpenTelemetry GenAI semantic conventions）——會造成元件間資料難以互通

## ⚠️ 查證缺口（誠實標注）

- 兩來源皆以「能自架就不買」為研究前提，通篇未明確指出任何 L3 元件真的無法自架，唯一潛在例外是 auto-distillation pipeline 用 frontier model 萃取 candidate 隱含的 LLM 推論成本，採購或自架未討論
- AWM 授權狀態兩來源直接矛盾——codex 稱授權不明，grok 稱 Apache-2.0；已由 Fable 5 補查 GitHub API 確認為 Apache-2.0 定案
- SkillHub 僅 codex 單一來源提及，grok 研究完全未涵蓋，其具體數字未經第二來源交叉驗證，定案前建議人工直接查看 repo 確認
- Opik 僅 codex 推薦為 observability 首選，grok 未獨立評估此選項，兩者實際功能/成熟度落差待人工比較後再定案
- Registry/eval 自架後端均查無官方硬體 sizing 數字，自架容量規劃仍需自行壓測
- SkillDisCo、MIND-Skill 與 COLLEAGUE.SKILL 三者皆查無可信獨立 GitHub repo 或 star 數，僅供研究方向參考
- 官方 Agent Skills 規格是否/何時會將 version 正式納入 frontmatter 頂層欄位，兩來源都只確認目前沒有，未查到官方路線圖
- Skill 市集供應鏈資安事件（Unit 42 與 1Password 關於 OpenClaw/ClawHub 攻擊面的報告）只有 grok 查到，codex 沒有獨立佐證此資安風險等級與時間軸
- 兩來源測試分層顆粒度不同——codex 提出七層完整測試模型，grok 提出三層模型，沒有明確對應/合併表，需人工定案
- Hermes Agent 的 pending-skill staged review 機制缺乏嚴謹的 auto-skill 品質 benchmark 佐證，僅屬流程模式參考
- Sigstore Cosign 的具體開源授權條款未見於兩份調查原文，需人工查證後再納入正式選型文件
- SKILL.md 與 MCP prompts/resources 之間是否有官方規劃中的 wire-format 互操作標準，兩來源都只確認目前沒有，未查到官方時程表
