# L4 記憶層（分層記憶、生命週期、混合檢索、Token budget）

**策略**：混合：🟢借用（框架借模式不借整套：Mem0 抽取管線／Graphiti bitemporal 投影／LangMem 分類法／cognee ingestion／Letta context 分層／MemOS 架構參考）＋ 🔴自研（PostgreSQL+pgvector canonical store／Lifecycle Manager／Hybrid Retrieval Engine／Token Budget Allocator 為系統核心）；本層 🔵採購為零

## 🏗️ 自研開發 Spec

Canonical Memory Store (PostgreSQL+pgvector+FTS) 為唯一 source of truth，承載六張 canonical 表 (memory/memory_revision/memory_source/fact_edge/memory_access_event/projection_checkpoint)，ACID 交易保證版本與 provenance 一致性。Extraction Service 借鑑 Mem0 與 MemOS 的 prompt-based LLM structured 抽取模式，以 content_hash 去重。Lifecycle Manager 驅動 captured→extracted candidate→validated→active→consolidated/superseded/retracted/expired→purged 狀態機，所有變更透過 append-only revision 完成，不覆寫既有列。Async Projection Pipeline 消費 PostgreSQL outbox 事件，非同步重建 pgvector/Qdrant 向量索引、FTS lexical 索引、Graphiti/Neo4j graph 投影（皆可重建、非 canonical）。Hybrid Retrieval Engine 實作 filter→[BM25/vector/graph 多路召回]→RRF 融合→cross-encoder rerank（bge-reranker-v2-m3）→time/utility 評分→MMR→token-budget packing 全流程；Token Budget Allocator 橫切貫穿每階段，取代最終截斷。MemScheduler 風格 Async Control Plane 負責 working-memory replacement 與 activation-memory refresh。核心資料模型：三維正交分類 Cognitive kind (episodic/semantic/procedural) × Representation (textual/activation/parametric) × Residency (working/durable/archive)，禁止塌縮成單一 memory_type 欄位；fact_edge 表採 Graphiti 式 bitemporal 四時間戳 (valid_from/valid_to+transaction_from/transaction_to)；刪除語意三態 forget/retract/purge 明確區分，不可混用單一 delete 欄位。

## ❌ 反模式（要避免）

- 不可把 Graphiti/Neo4j 當成 canonical audit store——僅作可重建的 graph projection，須離線評測證明 multi-hop/時間衝突確有提升才啟用
- 不可將 MemOS parametric (LoRA) 記憶層視為 production 可用——原始碼審計證實 load/dump/訓練注入邏輯仍是 TODO 骨架
- Token budget 不可留到最後才截斷——須貫穿檢索/rerank/MMR 每一階段
- Activation memory cache 不可用 pickle 做跨版本或不可信輸入的序列化——須改用安全格式並加相容性 metadata
- 中文 BM25 不可用 whitespace tokenizer——須自訂分詞 (Jieba/CKIP 等)
- 不可直接套用第三方單卡/單一場景的 reranker 延遲數字——須用自己的繁中語料與硬體實測
- pgvector 在 ANN+filter 情境下，若 filter 後只剩少量結果，低 ef_search 可能導致實際回傳筆數遠低於預期——須提高 ef_search 或改用 iterative scan/partial index/partitioning
- 不可用單一 memory_type 欄位籠統分類——須拆成 Cognitive kind/Representation/Residency 三正交維度
- 不可將社群 fork 誤認為官方 repo（如 Letta 應為 letta-ai/letta），也不可用衍生專案的授權條款代表原始專案的授權
- 不可將單一專案自報或第三方部落格的 benchmark 數字當成可信的跨系統比較依據——須區分官方一手數據與第三方非獨立驗證數據
- 不可將 github.com/getzep/zep 視為可自架的核心引擎方案——兩來源對此 repo 性質的描述互相矛盾，且 Community Edition 路線已知 deprecated，應以 Graphiti 作為自架替代
- 不可在原地覆寫記憶記錄——所有變更須走 append-only revision+supersedes 鏈，以維持可稽核性

## ⚠️ 查證缺口（誠實標注）

- MemOS/Letta/Graphiti 授權條款 confidence 落差：codex 明確標註三者皆為 Apache-2.0，claude-fallback 則明確表示未能確認；已由 Fable 5 補查 GitHub API 確認三者皆為 Apache-2.0 定案
- getzep/zep repo 性質矛盾：codex 稱其為已 deprecated 的 Community Edition，claude-fallback 稱其為 Zep 平台的 examples/integrations repo、非核心引擎，兩者對同一 URL 的定性完全不同，需人工查看該 repo 的 README/歷史紀錄釐清
- Letta 官方 repo 歸屬未確認：claude-fallback 指出搜尋只找到社群 fork，codex 則直接引用官方 repo；已由 Fable 5 補查 GitHub API 確認 letta-ai/letta 為官方且授權 Apache-2.0
- MemOS parametric (LoRA) 層成熟度描述落差：codex 直接讀原始碼證實明確 TODO、非 production 可用，claude-fallback 僅從論文/部落格取得架構層級描述，未觸及程式碼細節，建議以 codex 結論為準且應重新 clone repo 複核
- 跨系統 benchmark 不可信、且部分數字僅單方查得：MemOS 的 LoCoMo/LongMemEval 分數、token savings 只出現在 claude-fallback；Mem0 論文的延遲/token 成本數字只出現在 codex，正式決策前都必須用自建繁中 evaluation harness 重新驗證
- RRF「91% recall@10」與 Graphiti+Neo4j「P95 約 300ms」數字未經查證：兩者皆只出現在 claude-fallback，且來源本身已被標註為第三方部落格、未附資料集/baseline 細節，codex 完全沒有提及，建議視為不可信
- Reranker 選型未收斂：codex 建議 bge-reranker-v2-m3（多語，適合繁中），claude-fallback 舉例 ms-marco-MiniLM-L-6-v2（偏英文）與 Cohere Rerank API（商用），兩者未收斂到同一結論，且都沒有繁中語料下的實測數字
- 向量 DB 比較深度不足：兩來源都只深入比較 pgvector 與 Qdrant，Milvus/Weaviate 等替代方案僅被點名提及、未實際評測，不足以支持 Qdrant 優於 Milvus/Weaviate 的結論
- cognee 的記憶生命週期完整度只被單一來源檢視：codex 明確指出未找到官方文件描述完整 bitemporal 版本/salience decay 公式/rollback 協議，claude-fallback 對此完全沒有觸及
- Embedding model 選型兩來源皆未提及：整個混合檢索 pipeline 的前提是有 embedding model 做向量化，但兩份調查都沒有明確推薦具體的 embedding model
- SQLite 作為記憶儲存的生產可行性未被驗證：claude-fallback 明確表示未查到針對 agent 記憶場景的直接評測資料，codex 只討論 FTS5 BM25 函數機制細節，此點兩來源方向一致（僅適合 prototype）但都缺乏支持數字
- 兩份調查皆為桌面研究、非實測：所有 star 數、成熟度、benchmark 數字都是調查當下的網路公開資訊快照，且都未經任何一方在繁中生產環境實際部署驗證，正式決策前應重新核實現況
